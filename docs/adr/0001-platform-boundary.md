# ADR 0001. Граница платформы и ядра версионирования

Статус: proposed. Дата: 2026-11-06.

Уточнено: 2026-11-09. Статус сохранён.

## Контекст

Платформа предоставляет совместную работу над проектами, а ядро описывает версии данных и условия экспериментов. Разделение репозиториев не требует разделения процессов. Архитектура пока предложена: наличие компонента на схеме не подтверждает его реализацию.

Для первого сценария рассматривается один заранее выбранный доверенный ML-пайплайн. Минимальная платформа должна представлять историю и результаты операций ядра, не требуя собственной системы управления заданиями.

## Предложение

Подключать ядро как отдельный Go-модуль через адаптер платформы в серверном приложении. Сетевой сервис ядра не является обязательным условием. Ядро должно оставаться пригодным для использования без HTTP API, пользователей и интерфейса платформы.

Ядру принадлежат правила идентичности и неизменяемости версий, снимки условий, регистрация завершённых запусков, сравнение и построение плана восстановления. Платформа не дублирует эти правила. Она предоставляет адаптер ядра, необходимые механизмы хранения и HTTP API, отображает результаты и обеспечивает выбранный режим доступа. Управление заданиями и собственный исполнитель остаются расширением.

Сначала проверяется полный цикл ядра и CLI без платформы. Затем добавляются минимальный HTTP API и простой веб-интерфейс: список и история запусков, просмотр плана восстановления и сравнение двух запусков. Для MVP достаточно одного проекта и одного пользователя, допускается простая базовая аутентификация. Полноценное управление проектами, членством и RBAC не входит в обязательный состав. Граница минимального режима и будущего многопользовательского доступа описана в [ADR 0002](0002-project-access.md).

Проектная принадлежность ресурсов должна передаваться через согласованный контракт; конкретные типы и сигнатуры предстоит определить совместно с ядром. Ядро не принимает решений о членстве пользователей. Наличие идентификатора версии или плана восстановления само по себе не даёт платформе права читать объекты либо выполнять вычисление.

Снимок условий, попытка выполнения и отчёт сравнения рассматриваются отдельно. Повторное выполнение создаёт новую запись. План восстановления описывает необходимые материалы и действия; его получение не означает успешного восстановления, запуска или численного совпадения.

Первоначальная граница исполнения ограничена доверенным пайплайном. CLI или простой внешний скрипт получает план, восстанавливает материалы, подготавливает среду, запускает выбранный пайплайн и регистрирует результат как новый запуск со ссылкой на исходный снимок. Ни автоматический запуск внутри ядра, ни отдельный координатор или исполнитель платформы для этого не требуются. Приём произвольного кода, изоляция недоверенных заданий, HPC и распределённая отказоустойчивость остаются расширениями.

Платформа отображает раздельно структурную проверку, исход выполнения и сравнение результатов. Обязательный структурный критерий - доступность и целостность обязательных материалов и соответствие восстановленных условий исходному снимку. Успешное выполнение желательно продемонстрировать. Для метрик используется заранее зафиксированное правило конкретного пайплайна, структурный diff сам по себе не даёт заключения о численной воспроизводимости. Контракты определяются в [ADR восстановления](https://github.com/m1ssha/scientific-mlops-core/blob/main/docs/adr/0007-recovery.md) и [ADR сравнения](https://github.com/m1ssha/scientific-mlops-core/blob/main/docs/adr/0008-comparison.md) ядра.

## Рассмотренные варианты и причины

| Вариант | Оценка |
| --- | --- |
| Тонкая платформа и ядро как Go-модуль | Предлагается: сохраняет самостоятельность модели версий и позволяет проверить сквозной сценарий без дополнительного сетевого протокола. |
| Правила версий внутри платформы | Уменьшает число границ в начале, но связывает модель версий с доступом и интерфейсами, затрудняя самостоятельное использование ядра. |
| Ядро как отдельный сетевой сервис | Даёт независимое развёртывание, но требует протокола, обработки сетевых отказов и отдельной границы доверия до подтверждения такой потребности. |

## Последствия

Изменения контрактов ядра потребуют проверки совместимости адаптера и версии Go-модуля. Разделение ответственности не означает общей транзакции между метаданными и объектами. Порядок публикации и обработку незавершённых операций нужно согласовать отдельно.

В режиме с аутентификацией платформа сохраняет ответственность за авторизацию каждого обращения, включая чтение по плану восстановления. Локальный доверенный режим с фиксированной личностью не подтверждает изоляцию нескольких пользователей. Выбор БД, объектного хранилища, веб-фреймворка и способа развёртывания этим ADR не фиксируется, очередь заданий не обязательна.
